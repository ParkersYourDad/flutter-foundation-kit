# ADR-0007: Initial Flutter and Native Toolchain Baseline

- **Status:** Accepted
- **Date:** 2026-11-04
- **Decision owner:** Repository owner
- **Workstream:** Phase 01 — Platform and toolchain
- **Verification:** Pending GitHub Actions scaffold generation and Android/iOS build smoke tests

## Context

The starter must be created, built, and verified directly in GitHub without requiring a local development environment. GitHub-hosted macOS runners provide Android and iOS build environments. Independent version selection for Flutter, Gradle, Android Gradle Plugin, Kotlin, and native SDKs creates avoidable compatibility risk.

## Options considered

### A — Use Flutter stable release and its generated Android defaults

Benefits:
- The Android matrix is maintained and exercised by Flutter's project-generation tooling.
- Keeps the native scaffold aligned with the selected Flutter SDK.
- Avoids guessing AGP, Gradle, Kotlin, compile SDK, target SDK, and NDK versions independently.

Costs:
- Generated defaults may change with later Flutter releases.
- A required native plugin may require a newer version or migration.

### B — Select the newest version of each tool independently

Benefits:
- Could expose newer platform APIs sooner.

Costs:
- Versions may not be tested together.
- AGP 9 changes Kotlin and Android Gradle DSL behavior.
- Independent updates create more debugging and maintenance work.

## Decision

Pin the initial stable SDK to **Flutter 3.47.9 stable**, which bundles **Dart 3.13.7**.

Use the version constants from Flutter 3.47.9's own Android project generator:

| Tool/setting | Value |
|---|---:|
| JDK | 17 |
| AGP | 9.1.0 |
| Gradle | 9.3.1 |
| Kotlin Gradle Plugin | 2.4.0 |
| compileSdk | 36 |
| targetSdk | 36 |
| Build Tools | 36.0.0 |
| NDK | 28.2.13676358 |
| minSdk | 24 |

Retain the compatibility values generated by the same Flutter template:
- \`android.newDsl=false\`
- \`android.builtInKotlin=false\`

Do not turn on the AGP new DSL or built-in Kotlin manually until all selected plugins are confirmed migrated and an explicit build verification passes.

For iOS, use Xcode **26.6** with the iOS 26.5 SDK on macOS 26.2 or later. Use GitHub Actions \`macos-26\` for iOS CI and explicitly select Xcode 26.6. This meets Apple's current Xcode 26+/iOS 26 SDK upload requirement while remaining on a stable Xcode 26 release.

Use Swift Package Manager as Flutter's default iOS/macOS native dependency manager. CocoaPods fallback is permitted only for a required plugin that has not migrated; such a dependency needs a recorded risk because the CocoaPods registry is scheduled to become read-only on 2026-12-02.

Forui 0.27.7 is currently compatible with the Flutter 3.47 minimum stated by its publisher. This is not final package approval; package selection remains in Phase 02.

## Consequences

Positive:
- One known, stable Flutter/Dart version.
- Android versions are generated from Flutter's matching source, not chosen independently.
- iOS builds use a stable Xcode release satisfying current upload requirements.
- SwiftPM avoids making CocoaPods a default dependency.

Trade-offs:
- Newer stable Flutter releases require a deliberate matrix update.
- A plugin that lacks SwiftPM support may trigger CocoaPods fallback and requires a risk review.
- Local Windows development cannot perform iOS builds; macOS CI is mandatory for iOS verification.

## Revisit conditions

Revisit when a newer Flutter stable release is intentionally adopted, Flutter's generated Android defaults change, a required dependency changes minimum native requirements, Apple/Google submission policy changes, or a reproducible build failure demonstrates an incompatibility.
